# 豆瓣电影数据采集项目（约 1000 部）

一套**零第三方依赖**（只用 Python 标准库）的豆瓣电影数据采集工具。目标：把电影资料库、
评分分布、短评三类数据抓下来存进本地数据库，最后导出成 CSV / Excel 做分析。

> **本机已跑完一遍**（2026-10-13 ~ 10-14，共 1052 部作品、942 部带评分分布、4695 条短评）。
> 成品在 `export\`，**数据字典与覆盖度说明见 [数据说明.md](数据说明.md)**。想继续补数据看该文档第八节。

> **影人档案（`people` 表）本次不采集** —— 用户明确不需要单独的影人表。导演/主演的**姓名**
> 在 `movies` 表的 `directors` / `actors` 两列里，影人 id 在 `director_ids` / `actor_ids` 两列里
> （`movie` 阶段就有）。想补影人档案：跑 `crawl.py people`，再把 `crawl.py` 里
> `EXPORT_TABLES` 中被注释的两行取消注释。

> **可视化页面（ECharts + HTML/CSS/JS）** —— 在 `web\` 文件夹里：双击 `web\index.html` 就能看，
> 不需要装任何东西、不需要联网。**六屏可点击切换**：`01 概览 / 02 类型与年代 / 03 国家与地区 / 04 短评 / 05 建模 / 06 榜单`，
> 共 9 张图 + 17 个区块 + 6 组巨型 KPI（顶部的口径 × 年代筛选条仍在，默认收起）。
> 六屏合图见 `web\六屏总览.png`，改版前后对照见 `web\改版对比_20261020.png`。
> 代码怎么改见 **`01_可视化页面\说明文档.md`**（含"常见改法速查"表）；
> 数据由 `analysis\01_build_dataset.py` → `analysis\02_export_web_data.py` 生成到 `web\js\data.js`。

> **完整项目报告（给老师和同学展示用）** —— **`02_分析报告\报告.md`**：
> 采集 → 清洗 → 可视化 → 建模 全流程，含结论、图表与可复现命令。
> 建模的细节与全部指标另见 **`02_分析报告\建模报告.md`**。

> **为什么零依赖**：你不需要 `pip install` 任何东西，在 PyCharm 里打开就能跑。
> 唯一可选的依赖是 `openpyxl`（只影响"额外导出一份 .xlsx"；没装就只导 CSV，Excel 照样能开 CSV）。

## 4. 跑全量（3 步）

```bash
python crawl.py discover   # 1. 发现电影：攒够 1000 个 id
python crawl.py movie      # 2. 逐部抓资料（一页包办：资料 + 评分分布 + 热门短评）—— 最慢
python crawl.py export     # 3. 导出 CSV / Excel 到 export/
python crawl.py stats      # 随时看进度
python crawl.py retry      # 把"失败过"的条目清零，让下次运行重新尝试
```

或直接双击 `run_all.bat`。

**中途可以随时 Ctrl+C，重新运行同一条命令会从断点继续，不会重复抓。**

### 大概要跑多久（按默认限速估算，1000 部）

| 阶段 | 请求量 | 预计耗时 |
|---|---|---|
| discover | 100~200 次 | 10~30 分钟 |
| movie | 约 1100~1200 次 | **约 8~10 小时**（瓶颈是豆瓣的验证码墙，见第 6 节） |
| export | 0 次 | 几秒 |

**为什么这么慢**：不是程序的问题，是豆瓣对电脑端页面有人机验证墙——同一 IP 大约连续抓
**10 个页面**就会被挡（返回"禁止访问"页），要等 **2~3 分钟**才恢复。所以可持续速度大约是
**每分钟 2~3 个页面**。程序不会去撞墙：每抓 9 个页面主动休息 3 分钟（`BURST_REST["pc"]`），
万一还是被挡，就自动等一会儿再继续（`SHORT_PAGE_WAIT` / `BLOCK_SLEEP`），
**挂着跑就行，不用人守着**；也可以睡一觉起来看结果。

想更保守（例如怕影响家里其他人上网）：把 `config.py` 里的 `DELAY_PC` 调到 `(20.0, 30.0)`，
总时长会拉长到 12 小时以上，但更不容易撞墙。

## 5. 数据说明

全部存在 `data/douban.db`（用 DB Browser for SQLite / Navicat 都能打开）。
`export/` 下会导出 4 个 UTF-8-BOM 的 CSV，双击就能用 Excel 打开：

| 表 / CSV | 一行是什么 | 主要字段 |
|---|---|---|
| `movies` / `movies.csv` | 一部电影 | id, title, original_title, year, subtype(电影/剧集), genres, countries, languages, durations, pubdate, release_date, aka, directors, actors, tags, rating_value, rating_count, rating_star, rating_num, votes, **rating_p5~rating_p1(五星到一星占比)**, comment_count, review_count, imdb, pc_runtime, honor(Top250 名次), intro, cover_url, url |
| `movie_people` / `movie_people.csv` | 一条"某人 × 某片 × 某角色" | movie_id, people_id, role(导演/演员), name, character(角色名), ord |
| `people` / `people.csv` | 一位影人 | id, name, latin_name, gender, birthday, born_place, imdb, aka_cn, aka_en, intro, avatar |
| `comments` / `comments.csv` | 一条短评 | comment_id, movie_id, content, rating(星级), create_time, ip_location, user_id, user_name, votes(有用数) |

`movies` 表上有 4 个进度标记：`detail_done` / `rating_done` / `celeb_done` / `comments_done`
—— 这就是断点续爬的原理（哪个阶段抓过就打上标记，重跑只抓没标记的）。

**关于"电影"和"剧集"**：豆瓣的搜索接口会把电视剧、综艺一起带出来，它们的 `subtype` 是 `tv`。
只要电影的话，导出后按 `subtype='movie'` 过滤即可。

## 6. 反爬说明（重要，建议读一遍）

本项目对付豆瓣的思路是"**慢 + 稳 + 可续**"，不是硬刚。
下面这些阈值都是 2026 年在真实抓取中一条条量出来的，**改代码前请先读一遍**：

| 通路 | 实测表现 | 应对 |
|---|---|---|
| 列表接口 `j/new_search_subjects`（发现用） | 连发 50+ 次仍然 200，很宽容 | `DELAY_API` 3~6 秒 |
| 手机接口 `m.douban.com/rexxar/...` | 约 **72 次**后开始返回 `HTTP 400 {"msg":"subject_ip_rate_limit","code":1309}` | 已不用它做主通路（见下） |
| 电脑端 `movie.douban.com/subject/<id>/` | 约 **10 个页面**后返回 **1041 字节的"禁止访问"页**（腾讯 TCaptcha 人机验证） | 每 9 页主动休息 3 分钟 + 撞墙等待 |
| 全站 | 早期用 1.2~2.4 秒间隔猛跑，4 分钟约 90 次后**全站 403**（连首页都 403） | 已把间隔放宽数倍 |

1. **限速**：接口 3~6 秒、电脑端页面 **16~24 秒**（都是随机取值），在 `config.py` 里可调。**不要调小**。
2. **人机验证墙（最重要的一条）**：电脑端详情页连续抓约 10 个之后，豆瓣会返回一个 1041 字节的页面：
   `<title>禁止访问</title>` … *"你访问豆瓣的方式有点像机器人程序。为了保护用户的数据，请向我们
   证明你是人类"* … 加载腾讯 TCaptcha（appid 2003459237）→ POST `/misc/sorry`。
   **这是真验证码，代码解不了**（它和下面第 4 条那个 sha512 哈希题是两回事）。
   实测它 **2~3 分钟后自行解除**，然后又能抓约 10 个页面 —— 所以可持续速度约 **每分钟 2~3 个页面**。
   程序的处理：撞墙后先睡 `SHORT_PAGE_WAIT`（180 秒）重试同一条；还是墙，就熔断、
   由主程序睡 `BLOCK_SLEEP`（600 秒）后自动续爬，最多自动续 `MAX_BLOCK_WAITS`（40）轮。
3. **熔断保护**：程序发现**连续 6 次 403/429**、或一个阶段里**连续 8 次失败**，会主动停下
   （不会硬冲到你被封），已经抓到的数据全部保留。
   （这道闸是用教训换来的：早期版本没有它，500 多部电影在限流期间被静默标成"失败"。）
4. **豆瓣的哈希挑战**：电脑端页面有时会先返回一个约 2.9KB 的挑战页，要求算出一个 nonce 使
   `sha512(cha + nonce)` 的前 4 位是 0，再带 `{tok, cha, sol, red}` POST 到 `https://sec.douban.com/c`。
   本程序用 `hashlib` 自己暴力求解（通常几十毫秒），POST 的响应**直接就是目标页面**，
   而且这个会话就此解锁，后面的请求不会再被挑战。
   注意：POST 时**不能带 `Origin` 头**，带了会直接 403（这个坑已经踩过并写在代码注释里）。
5. **为什么改走电脑端页面**：手机接口给不了"五星~一星占比"，而且它 72 次就限流。
   电脑端页面一页里同时有 **全部电影资料 + 评分分布 + 热门短评**，等于
   "1 次请求 = 原来 3 个接口"，总请求量从约 3000 次降到约 1000 次，也更不容易被盯上。
   （`detail` / `rating` / `comments` 三个子命令保留着，作为备用通路。）
6. **自动退避**：空页先等 20 秒再确认一次；普通失败按 20/45/90 秒重试 3 次；
   403/429 单独按 60 秒重试。
7. **抓失败不会算"抓过"**：某一条（某部电影/某位影人）抓失败时，程序**不会**给它打完成标记，
   只记一次失败次数，所以下次跑同一条命令还会重试它。连续失败超过 `MAX_FAIL_PER_ITEM`（默认 3）次
   才暂时放弃 —— 这时跑 `python crawl.py retry` 就能让它重新可抓。
   （对照老项目：它把"失败"也标成"已完成"跳过，于是那些条目永久缺数据。）
8. **不用登录**：本项目只访问免登录通路，**不需要你的豆瓣账号密码**。
   请不要把账号密码写进代码 —— 这也是我们分析的那个 2018 年老项目最大的教训。
9. **合规**：仅供个人学习与研究使用。请遵守豆瓣的用户协议与 robots 规则，
   不要用于商业用途，不要大规模转载抓到的内容（简介/短评的著作权属于原作者）。
   另外：如果豆瓣真的弹出了人机验证，请**人工去过一次**（浏览器里点一下），
   本项目不提供绕过验证码的方案。

## 7. 想改哪里，改什么

打开 `config.py`，常用参数都在最上面：

| 参数 | 默认 | 含义 |
|---|---|---|
| `TARGET_MOVIES` | 1000 | 目标电影数（2026 决定：先做 1000 部左右） |
| `COMMENTS_PER_MOVIE` | 5 | 每部电影抓几条短评（手机接口最多给约 100 条） |
| `PEOPLE_PER_MOVIE` | 6 | 每部电影关联几位影人 —— **本次不跑 people 阶段，此项不生效** |
| `DELAY_API` | (3.0, 6.0) | 列表接口请求间隔秒数区间 |
| `DELAY_PC` | (6.0, 9.0) | 电脑端详情页请求间隔秒数区间（**成组节奏由 `BURST_REST` 控制**） |
| `BURST_REST` | `{"pc": (9, 180)}` | 电脑端每抓 9 个页面主动休息 180 秒（验证码墙的配额是"约 10 页 / 2~3 分钟"） |
| `SHORT_PAGE_WAIT` | 180 | 撞到"禁止访问"壳页后等多少秒再试同一条 |
| `BLOCK_SLEEP` / `MAX_BLOCK_WAITS` | 600 / 40 | 熔断后自动睡多久再续爬、最多续多少轮 |
| `MAX_PAGES_PER_QUERY` | 12 | 每个查询最多翻多少页（一页 20 条） |
| `MAX_REQUESTS_PER_RUN` | 0 | 单次运行最多发多少请求（0=不限；想"跑一会儿歇一会儿"就设 800） |
| `BLOCK_THRESHOLD` | 6 | 连续多少次 403 就熔断停止 |
| `MAX_CONSEC_FAIL` | 8 | 一个阶段里连续失败多少次就停下（防止接口整体挂了还傻跑） |
| `MAX_FAIL_PER_ITEM` | 3 | 同一个条目最多自动重试几次（超了要 `crawl.py retry` 才再试） |
| `RATING_BANDS` / `YEAR_BANDS` / `GENRES` / `COUNTRIES` / `SORTS` | — | 发现阶段的查询矩阵，决定能铺出多少部电影 |

**查询矩阵**是抓够 1500 部的关键：豆瓣的分类接口单条件翻不了太深（几百页就空），
所以要靠"评分区间 × 年份区间"、"类型 × 评分区间"、"地区 × 评分区间"这些组合多路并进，再按 id 去重。
默认矩阵有 100+ 条查询，每条最多翻 12 页（240 条），理论上限两万多条记录，去重后预计能铺出 2000 部以上
（实测 5 条查询 ×2 页 = 200 条记录，去重后仍是 200 部，几乎没有重复）。想要更多就往 `GENRES` / `YEAR_BANDS` 里加。
真跑不够 1800 部时 `crawl.py stats` 会告诉你实际用了多少条查询，照着加就行。

想改抓到的字段：改 `parsers.py` 的对应函数，再到 `storage.py` 的表结构里加列（新库自动建表）。

## 8. 常见问题

- **一堆 403 / 数据全是空**：被限流了。程序一般会自己等；如果它提前退出，等 30~60 分钟再跑
  （`python crawl.py movie`），或把 `DELAY_PC` / `DELAY_API` 调大。已有数据不会丢。
- **日志里出现"禁止访问"或"空壳页"**：撞上人机验证墙了，这是正常的节流现象，代码会自己等；
  想确认墙的样子，看 `logs/short_page_1.html`（程序自动存下来的前几份原文）。
- **`movie` 阶段很慢**：正常，约每分钟 2~3 个页面，1000 部要 8~10 小时。
- **短评为什么只有 5 条**：电脑端详情页只渲染热门 5 条左右，这是豆瓣的限制，不是 bug。
  想要更多短评需要另一套方案（登录 cookie + 专门翻短评页 + 更慢的限速）。
- **电影数和预期差很多**：`python crawl.py stats` 看"发现的查询数"。正常会用到几十上百条查询；
  如果只有个位数，说明前期就被限流了，把间隔调大后重跑（已翻的页不会重翻）。
- **想重新来一遍**：删掉 `data/douban.db` 即可（或只删该文件里的某些行）。
- **想只留电影、不要剧集**：导出后按 `subtype` 过滤（`movie` = 电影，`tv` = 剧集）。

## 9. 设计取舍（为什么这么写）

1. **零依赖**：不用 requests / Scrapy / lxml，避免"装不上包/版本冲突"卡住你；解析用正则 + `html.parser`。
2. **SQLite 存状态**：进度全在库里，程序崩了、网断了、关电脑了，重跑都接着来
   （对照老项目：它用 `codecs.open(...,'w')` 直写 JSON，一重跑就把上次的数据清空了）。
3. **一个阶段一个命令**：出问题只重跑那一段。
4. **电脑端一页包办**：`movie` 阶段每部电影只发 1 次电脑端页面请求，一页里同时取到
   电影资料、评分分布、热门短评（手机接口给不了五星占比，而且 72 次就限流）。
   代价是必须接受豆瓣约"10 个页面 / 2~3 分钟"的节流节奏。
5. **熔断 + 退避 + 自动续爬**：宁可慢，不要让你的 IP 被拉黑；撞墙就等，等完自己接着爬。
